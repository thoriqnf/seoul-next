# Developer Guide: Next.js Server-Side Rendering (SSR) & Common Pitfalls (Week 3 Day 2)

This guide walks you through the core concepts of Next.js Server-Side Rendering (SSR). You will learn how to fetch data directly on the server, fetch multiple resources concurrently, stream parts of the page asynchronously using `<Suspense>`, and diagnose/resolve common hydration mismatch and client global object errors.

---

## Learning Objectives & Topics Covered

1. **React Server Components (RSC)**: Fetching data in server components directly with async/await.
2. **SSR Parallel Fetching**: Using `Promise.all` to query multiple endpoints in parallel to optimize rendering speeds.
3. **SSR Streaming (Suspense & loading.tsx)**: Streaming HTML segments to the browser while slower data fetches resolve.
4. **Common Pitfall - Hydration Mismatch**: Fixing discrepancies between markup generated by the server and matching markup rendered by the browser (e.g. dates, random values).
5. **Common Pitfall - Client API Crashes**: Preventing runtime server crashes due to browser-only globals (like `window` or `localStorage`) during pre-rendering.

### Phase 2: Server-Side Data Fetching

#### Step 2 (`// TODO SSR 2`): Basic SSR Data Fetching
In Server Components, you can mark the functional component itself as `async` and fetch data directly using `fetch` or `axios`.
```typescript
// Fetch flowers directly inside a Server Component
async function getFlowers(): Promise<Flower[]> {
  const res = await fetch("https://64ca45bd700d50e3c7049e2f.mockapi.io/flowers", {
    cache: "no-store", // Opt-out of build-time static generation caching for dynamic SSR
  });
  if (!res.ok) throw new Error("Failed to fetch flowers");
  return res.json();
}
```

#### Step 3 (`// TODO SSR 3`): Parallel SSR Data Fetching
If you need to load data from multiple endpoints, fetching sequentially (awaiting the first, then awaiting the second) causes a network waterfall. Use `Promise.all` to execute them in parallel:
```typescript
const [flowers, announcements] = await Promise.all([
  getFlowers(),
  getAnnouncements(),
]);
```

### Phase 3: Streaming & Suspense

#### Step 4 (`// TODO SSR 4`): Streaming with React Suspense
By wrapping a slower server-rendered component inside `<Suspense>`, Next.js can send the static parts of your layout instantly and stream the slow-rendering component once its async operation resolves.
```jsx
import { Suspense } from "react";

// In your page layout:
<Suspense fallback={<div className="animate-pulse">Loading announcements...</div>}>
  <SlowAnnouncements />
</Suspense>
```

### Phase 4: Fixing Common SSR Pitfalls

#### Step 5 (`// TODO SSR 5`): Resolving Hydration Mismatch
Hydration mismatch happens when the content rendered on the server differs from the initial render on the client (e.g. displaying local time, dates, or random IDs).
* **Fix**: Force the component to only render dynamic state on the client using a simple `isMounted` state inside `useEffect`:
```typescript
const [time, setTime] = useState<string>("");

useEffect(() => {
  setTime(new Date().toLocaleTimeString());
}, []);

// Before mounting is completed, output a static/placeholder string
if (!time) return <span>Loading time...</span>;
return <span>{time}</span>;
```

#### Step 6 (`// TODO SSR 6`): Handling Browser-Only API Crashes
During SSR, React renders the code on the Node.js server first. Calling client-only properties like `window` or `localStorage` will throw reference errors: `window is not defined`.
* **Fix**: Guard the call by checking if `window` is defined, or read browser values strictly inside `useEffect` (which runs only on the client):
```typescript
const [theme, setTheme] = useState<string>("default");

useEffect(() => {
  if (typeof window !== "undefined") {
    const saved = localStorage.getItem("theme") || "light";
    setTheme(saved);
  }
}, []);
```

## How to Test & Verify
